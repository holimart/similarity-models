# Rebuild live camera translation with open components

The open-source landscape has **one especially direct but very immature Google-Translate-camera-style attempt**: `ar-camera-translate`, an Android/Flutter app whose README claims continuous OCR, on-device translation, and position/angle-aligned text. The evidence does not establish a maintained, independently tested equivalent, and the project lacks a visible license; several other apps offer camera OCR or translation without proving continuous anchored replacement. The more mature route is to assemble platform OCR and translation with a custom tracking/rendering layer, while recognizing that these vendor SDKs are not open-weight stacks. Open OCR and MT alternatives are available, but **text removal, stable tracking, and scene-matched rendering remain integration work**. For Czech↔English, ML Kit documents Czech support in both OCR and translation; open model options include Bergamot/Marian, OPUS-MT, and Argos, each with different packaging and license questions. No reviewed source supplies comparable end-to-end latency or quality measurements for the complete camera experience.

## Only one app clearly claims anchored live-camera replacement

“Camera translation” describes several different products: a photo OCR tool, a live preview with text recognition, speech-caption overlays, or the full experience of repeatedly detecting scene text and drawing translations at the same location. This distinction changes the shortlist. The strongest exact-match lead, [ar-camera-translate](https://github.com/crlx1q/ar-camera-translate), is a Flutter Android app whose README claims real-time ML Kit OCR, automatic language identification, offline translation, and translated text positioned and rotated over source text. Yet the repository shows only 24 commits, no visible license, and no verified release or independent device evaluation. It expressly says its OCR recognizes Latin, Chinese, Japanese, Korean and Devanagari scripts—not Cyrillic or Arabic—so its advertised translation-language count should not be mistaken for source-script coverage. Its claimed overlay is not evidence of source-text inpainting or robust tracking under camera motion.

## Mature components solve only the first half of the experience

OCR engines can return text and boxes, but they do not provide persistent identity or a correctly transformed overlay by themselves. Google’s ML Kit Text Recognition v2 returns hierarchical blocks, lines and elements with bounding geometry and documents real-time camera processing; its guidance recommends dropping incoming frames while a detector is busy and using CameraX latest-frame backpressure. The official [ML Kit quickstart](https://github.com/googlesamples/mlkit/tree/master/android/vision-quickstart) is an implementation reference, not a translator app. ML Kit is platform/vendor-dependent rather than an open-weight component. Its bundled recognition model is about 4 MB per script architecture; the Play-services unbundled option is about 260 KB but can require a first-use download. ([ML Kit Android guide](https://developers.google.com/ml-kit/vision/text-recognition/v2/android))

For a more open OCR stack, [PaddleOCR](https://github.com/PaddlePaddle/PaddleOCR) offers Apache-2.0 software, configurable deployment, Android/iOS demos and a browser SDK based on ONNX Runtime Web/OpenCV.js. Its mobile samples are implementation starting points, not proof of current streaming readiness; the Android demo documentation is dated. [EasyOCR](https://github.com/JaidedAI/EasyOCR) is Apache-2.0, Python/PyTorch-oriented, supports quadrilateral detections and confidence, and advertises 80+ languages—useful for prototyping or a server, less turnkey for an embedded camera loop. [Tesseract](https://github.com/tesseract-ocr/tesseract) is a mature Apache-2.0 OCR engine with positional output formats, but not a real-time camera UI or scene-text tracker. On iOS, Apple Vision plus AVFoundation is the most direct native starting point; it is not open source. ML Kit, Vision, and PaddleOCR should be benchmarked on the same Czech scene-text set rather than ranked by “real-time” labels or unrelated published timings. ([PaddleOCR deployment](https://github.com/PaddlePaddle/PaddleOCR/tree/main/deploy); [EasyOCR](https://github.com/JaidedAI/EasyOCR); [Tesseract](https://github.com/tesseract-ocr/tesseract); [Apple AVFoundation](https://developer.apple.com/documentation/avfoundation/capture_setup))

The app must own the rest of the live path: associate detections across frames, smooth quadrilateral corners, reject unstable text, cache translations, and map detector coordinates through rotation, mirroring, crop and preview scaling. A bounded asynchronous loop should process the newest available frame, not accumulate stale frames. Translate only when a stabilized text region changes. Without those steps, otherwise competent OCR can produce flickering words and lagging boxes. These are engineering recommendations; no reviewed repository provides this as a validated cross-platform full stack. ([ML Kit performance guidance](https://developers.google.com/ml-kit/vision/text-recognition/v2/android); [OpenCV optical flow](https://docs.opencv.org/4.x/d4/dee/tutorial_optical_flow.html))

## Czech-English translation is feasible, but model choice affects openness

For Czech Latin text, Google’s documentation explicitly lists Czech in ML Kit text recognition support, and ML Kit on-device Translation supports `cs` and `en`; language models are downloaded and managed on device. This is the simplest Android prototype path, but it is not an open-weight solution, and Google characterizes the translation API as suitable for casual/simple use rather than the highest-fidelity translation. Model availability, attribution guidance and actual signage/menu quality still need validation. ([ML Kit OCR language support](https://developers.google.com/ml-kit/vision/text-recognition/v2/languages); [Translation language support](https://developers.google.com/ml-kit/language/translation/translation-language-support); [ML Kit Translation](https://developers.google.com/ml-kit/language/translation))

For open deployments, test [Bergamot/Marian](https://github.com/browsermt/bergamot-translator) small Czech↔English models first where available: Bergamot targets consumer devices and supports native/WASM builds, while Marian is MIT and Bergamot is MPL-2.0. Mozilla’s archived Firefox Translations used Bergamot locally and included Czech, but the archived extension is not a maintained camera SDK; current model registry and exact artifact terms require checking. [Helsinki-NLP OPUS-MT](https://huggingface.co/Helsinki-NLP/opus-mt-cs-en) publishes separate cs→en and en→cs checkpoints (Apache-2.0 on those model cards); two directions mean two models unless a combined alternative is chosen. OPUS model repository materials also caution that some automatic scores use short/simple test sentences and can overstate practical performance. [Argos Translate](https://github.com/argosopentech/argos-translate) is a comparatively simple offline Python library with Czech and English packages and pivot translation when a direct pair is unavailable, though pivoting can reduce quality and the engine license does not settle each model package’s terms. ([Firefox Translations archive](https://github.com/mozilla/firefox-translations); [model registry](https://mozilla.github.io/translations/model-registry/); [OPUS-MT project](https://github.com/Helsinki-NLP/Opus-MT); [Argos package index](https://www.argosopentech.com/argospm/index/))

Broad multilingual models trade compactness for coverage. M2M100 418M lists Czech and English among 100 languages and an MIT model-card license, but FP16 weights alone are roughly 0.84 GB by parameter-count calculation, before runtime and activations. NLLB-200 distilled 600M covers 196 languages, but its model card lists CC-BY-NC-4.0 and says research rather than production deployment; it is a poor default for commercial products. Those parameter-derived storage figures are estimates, not package sizes or measured device RAM. No common phone latency benchmark was found for these translation options. ([M2M100 model card](https://huggingface.co/facebook/m2m100_418M); [NLLB model card](https://huggingface.co/facebook/nllb-200-distilled-600M))

## Inpainting and scene-matched text remain unsolved integration work

Rendering has two importantly different meanings. The simplest app can place a colored or translucent card behind translated text; this is robust and legible but does not recreate the original scene. A Google-like replacement attempts to remove source lettering, reconstruct hidden background, then fit translated text into the source plane. OCR geometry can locate a mask, but neither OCR nor translation supplies the missing background, original font, layout, color or temporal stability.

[LaMa](https://github.com/advimman/lama) is a research image-inpainting system taking an image and mask, not an OCR/translation renderer. [OpenCV inpaint](https://docs.opencv.org/4.x/df/d3d/tutorial_py_inpainting.html) offers simpler Telea and Navier–Stokes methods appropriate mainly to small regions; neither is semantic scene reconstruction. [ProPainter](https://github.com/sczhou/ProPainter) performs video inpainting from video and frame-wise masks, but is a batch/research-oriented GPU path with substantial memory costs and an explicit non-commercial NTU S-Lab license. [Segment Anything](https://github.com/facebookresearch/segment-anything) can generate masks but does not translate or inpaint; its code/model is Apache-2.0 while dataset terms are separate. None is an integrated live camera translator, and README or paper metrics for these components are not whole-app performance evidence. ([LaMa paper](https://arxiv.org/abs/2109.07161); [ProPainter paper](https://arxiv.org/abs/2309.03897); [SAM licensing](https://github.com/facebookresearch/segment-anything))

A plausible advanced renderer rectifies a detected text quadrilateral into a plane, expands it into a removal mask, inpaints only after text/geometry stabilizes, lays out translated glyphs in that plane, and projects the patch back with a homography. Tracking and cached repairs can reduce jitter and repeated computation. These are proposed application techniques, not demonstrated capabilities of the cited projects; natural background under lettering is unknowable from a single image, and translation changes line length and line breaks. Even exact font/style reconstruction is underdetermined from OCR text and boxes alone. Keep a card fallback for moving scenes, complex backgrounds or poor repair. ([LaMa](https://github.com/advimman/lama); [ProPainter](https://github.com/sczhou/ProPainter))

## Build a measured prototype before pursuing pixel-perfect replacement

The shortest Android route is Kotlin + CameraX + ML Kit OCR + ML Kit on-device `cs`↔`en` translation + a native Canvas/Compose overlay. Start with tracked translucent cards and an original/translated toggle; this tests real camera usability, Czech diacritics, translation, coordinate transforms and latency without letting inpainting dominate the schedule. It is a practical integrated stack, but not open-weight. For a reproducible open GPU reference, use Python/OpenCV + PaddleOCR (or EasyOCR) + OPUS-MT/Marian + OpenCV overlay; try LaMa separately on stable still crops. A browser prototype can combine `getUserMedia`, PaddleOCR.js and canvas/WebGL, but mobile-browser speed and permissions vary and require device testing. ([CameraX analysis](https://developer.android.com/media/camera/camerax/analyze); [PaddleOCR.js](https://github.com/PaddlePaddle/PaddleOCR/tree/main/paddleocr-js); [MDN getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia))

Evaluate with Czech signs, menus and packaging containing č/ř/ž/ě/š/ů/ý/á/í/é, small print, perspective, glare, curved surfaces and motion blur. Preserve Unicode and score OCR separately from MT; compare translation using both perfect transcription and real OCR output to isolate recognition damage. Measure cold model setup/download, end-to-end frame-to-first-stable-overlay latency (p50/p95), update interval, stale/dropped frames, RAM, thermal behavior and battery on actual mid-range devices. Evaluate background repair independently for removal quality and temporal flicker. Published OCR module times, desktop GPU results, MT BLEU/chrF and model parameter counts do not predict this end-to-end result. The notes found no comparable full-pipeline benchmark. ([ML Kit OCR guidance](https://developers.google.com/ml-kit/vision/text-recognition/v2/android); [OPUS-MT cs→en card](https://huggingface.co/Helsinki-NLP/opus-mt-cs-en); [PaddleOCR benchmarks](https://www.paddleocr.ai/main/en/version3.x/pipeline_usage/OCR.html))

Licensing needs an asset-by-asset inventory: app code, OCR engine, translation runtime, each model checkpoint/tokenizer, converted or quantized weights, inpainting assets, dependencies and fonts. A permissive engine does not automatically grant rights to separately distributed weights or datasets. In particular, verify missing app licenses before reuse, individual Argos package terms, and avoid ProPainter for commercial plans absent permission. Hearth’s Apache-2.0 first-party code does not replace its third-party/model notices. This is a technical summary, not legal advice. ([Hearth license and notices](https://github.com/Sal7one/Hearth); [Argos Translate](https://github.com/argosopentech/argos-translate); [ProPainter license](https://github.com/sczhou/ProPainter))

## Conclusion

The open ecosystem can support a useful live Czech-English camera translator today, but the credible product is a composition of components, not a clone found in one repository. The right first milestone is reliable region tracking and readable translation cards; replacement-quality scene reconstruction should be an optional later layer, judged on real moving-camera tests rather than still-image demos.

The most valuable project decision is therefore the desired openness boundary: choose native vendor SDKs for the fastest mobile validation, or accept model packaging and integration work for an open OCR/MT stack. Either way, success hinges less on an advertised language count than on Czech diacritics, stable geometry, sensible latency and fallback behavior measured end to end.
