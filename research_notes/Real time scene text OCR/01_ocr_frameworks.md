# Deployable OCR frameworks for real-time scene text

## Which frameworks provide the complete detection-and-recognition path, and how do their architectures and box outputs differ?

### Takeaway
For scene text, PaddleOCR and RapidOCR are the strongest turnkey deployment candidates in this set; EasyOCR and docTR offer accessible two-stage learned pipelines; MMOCR is a research toolbox with the broadest model choice; Tesseract is principally a recognition engine, while OpenCV supplies inference APIs and primitives that need trained models and pipeline assembly. Detector architecture and geometry are consequential: curved/rotated signage often needs polygon-capable detection, while horizontal rectangles are adequate only for simpler scenes.

### Cited Findings
- PaddleOCR packages scene OCR as a detection/recognition pipeline and currently advertises PP-OCRv6 model tiers (tiny/small/medium), unified multilingual recognition, and text spotting. The repository identifies Apache-2.0 licensing. The README’s newest headline speeds/accuracy are maintainer-reported, not an independent camera-stream benchmark. — [PaddleOCR repository](https://github.com/PaddlePaddle/PaddleOCR)
- EasyOCR explicitly combines CRAFT text detection with CRNN recognition (CNN feature extractor, recurrent sequence model, CTC decoding). `readtext` returns four-point box coordinates, text, and confidence. Its README describes an instantiated `Reader` as reusable and accepts OpenCV arrays, but the documented API is image-by-image rather than a video tracker/stream pipeline. — [EasyOCR repository](https://github.com/JaidedAI/EasyOCR)
- MMOCR is a modular PyTorch/OpenMMLab research toolbox. It includes detector choices such as DBNet/DBNet++, PANet, PSENet, TextSnake, DRRG, FCENet; recognizers include CRNN, ABINet, ASTER, MASTER, NRTR, SAR, SATRN, and SVTR. It also includes end-to-end spotting projects ABCNet/ABCNetV2 and SPTS. This gives flexibility, but installation depends on PyTorch, MMEngine, MMCV, and MMDetection and model/config selection is an engineering task. — [MMOCR repository/model zoo](https://github.com/open-mmlab/mmocr)
- docTR is a two-stage word detection-then-recognition library with selectable DBNet, LinkNet, or FAST detectors and CRNN, SAR, MASTER, ViTSTR, PARSeq, or VIPTR recognizers. Its predictor can return rotated boxes or straight boxes; `assume_straight_pages=True` is documented as its fastest option. The library is oriented toward document parsing, though its underlying models include scene-text architectures. — [docTR repository](https://github.com/mindee/doctr)
- Tesseract 4+ uses an LSTM neural OCR engine focused on line recognition; its core repo does not provide a learned scene-text detector. It recognizes crops or page-segmented input using page segmentation modes and produces text, hOCR, TSV, ALTO, and other output formats. A separate detector/cropper/tracker is needed for general camera scenes. — [Tesseract repository](https://github.com/tesseract-ocr/tesseract)
- RapidOCR is explicitly derived from converted PaddleOCR models, with the project presenting itself as an inference/deployment layer rather than a new detector family. Its current model list includes PP-OCRv4/v5/v6 detector, orientation classifier, and recognizer variants; converted artifact formats include ONNX, MNN, TensorRT, Paddle, and PyTorch. — [RapidOCR repository](https://github.com/RapidAI/RapidOCR); [model list](https://rapidai.github.io/RapidOCRDocs/main/model_list/)
- OpenCV’s `dnn::TextDetectionModel` supports DB and EAST, with `detect()` returning four-point quadrilaterals or `detectTextRectangles()` returning rotated rectangles. `TextRecognitionModel` supports CNN+RNN+CTC and greedy or CTC prefix beam decoding. The official example explicitly builds spotting by transforming/cropping detections and then calling recognition: OpenCV is an API/runtime foundation, not an opinionated end-to-end scene OCR product. — [OpenCV scene-text tutorial](https://docs.opencv.org/4.13.0/d4/d43/tutorial_dnn_text_spotting.html)

### Inferences
- For continuous video, frame acquisition, frame sampling, temporal association/tracking, duplicate suppression, and confidence smoothing usually need to be implemented around these OCR frameworks; the cited OCR APIs mostly expose per-image inference rather than persistent text-track semantics.
- DB-like segmentation detectors naturally support irregular polygonal text boundaries; EAST commonly predicts oriented rectangles. Output geometry is framework/model-dependent and should be checked for the exact selected model, rather than inferred from the project name.

### Gaps
- No same-data, same-hardware published comparison was located here for all six OCR frameworks on a camera/video stream. Published model scores and toolkit throughput claims cannot substitute for an application-specific end-to-end benchmark.
- Exact geometry and batching support vary by model/config/version in PaddleOCR, MMOCR, docTR, and RapidOCR; test the chosen deployment model rather than treating package-level statements as universal.

## What are the deployment, streaming, mobile, accelerator, language, and licensing tradeoffs?

### Takeaway
The clearest deployment focus is RapidOCR (multiple runtimes and language bindings, Android/iOS/C++/JVM repositories) and PaddleOCR (C++/browser and Android/iOS deployment documentation, plus GPU backends). OpenCV and Tesseract are mature embeddable components. MMOCR/docTR/EasyOCR are primarily Python deep-learning ecosystems; none of these project descriptions alone proves sustained real-time performance on the target camera, device, or thermal envelope.

### Cited Findings
- PaddleOCR supports CPU/GPU and high-performance backend selection including Paddle Inference, OpenVINO, ONNX Runtime, and TensorRT where compatible; its docs also link C++ local deployment, Android/iOS, and browser deployment. The high-performance-inference docs state Linux/x86-64 constraints for the described plugin setup and document CUDA/cuDNN/TensorRT version conditions—capabilities are not interchangeable across all models/platforms. — [PaddleOCR high-performance inference](https://paddlepaddle.github.io/PaddleOCR/latest/en/version3.x/inference_deployment/local_inference/high_performance_inference.html); [PaddleOCR repository](https://github.com/PaddlePaddle/PaddleOCR)
- RapidOCR lists ONNX Runtime, OpenVINO, MNN, Paddle, PyTorch, and TensorRT engines with version-dependent support and maintains Android, iOS, C++, .NET, and JVM project directories. It is a strong fit where portable inference-engine choice or a native-language deployment path matters; verify specific model-engine combinations in its versioned model list. — [RapidOCR repository](https://github.com/RapidAI/RapidOCR); [RapidOCR model list](https://rapidai.github.io/RapidOCRDocs/main/model_list/)
- EasyOCR can run CPU-only (`gpu=False`) or use PyTorch GPU support; the project documents language selection at model initialization, with constraints on which languages can be combined. Its README lists 80+ languages and common scripts. Its latest noted release is 1.7.2 (2024-09-24), so deployment teams should assess current issue/release activity and dependency compatibility. — [EasyOCR repository](https://github.com/JaidedAI/EasyOCR)
- MMOCR is Apache-2.0 and built on PyTorch plus OpenMMLab dependencies. Its supported model menu is broad, but the repository’s main-branch 1.0.0 release announcement dates to 2023; repository activity and dependency support should be reviewed for the particular intended stack. It is best characterized as flexible/research-oriented rather than a minimal mobile SDK. — [MMOCR repository](https://github.com/open-mmlab/mmocr)
- docTR is Apache-2.0, offers PyTorch and TensorFlow ecosystems in the project/topic documentation and GPU-ready Docker guidance, but its currently described installation prerequisite is Python 3.11+. Its documents cover API/Docker deployment rather than a first-party embedded mobile SDK. Maintenance responsibility is now stated as t2k GmbH. — [docTR repository](https://github.com/mindee/doctr)
- Tesseract 5 is a mature native C/C++ engine with a C API, CLI, and broad wrappers. The engine repo is Apache-2.0; it depends on Leptonica (BSD 2-clause noted by the project), and model/data files should be checked separately. It supports over 100 languages, but scene text performance depends heavily on crop quality and page segmentation. — [Tesseract repository](https://github.com/tesseract-ocr/tesseract); [Tesseract language data table](https://tesseract-ocr.github.io/tessdoc/Data-Files-in-different-versions.html)
- OpenCV is Apache-2.0 and highly deployable as a general computer-vision library, including DNN APIs, CPU and accelerated backends, and camera/video I/O. For its cited text recognition API, the supported recognizer is CNN+RNN+CTC and inference recognition batch size is documented as one. Shipped pretrained example models have limited language coverage (the cited CRNN variants cover alphanumeric English and one Chinese vocabulary; detector models are noted as English-only ICDAR15 or English/Chinese TD500). — [OpenCV repository](https://github.com/opencv/opencv); [OpenCV scene-text tutorial](https://docs.opencv.org/4.13.0/d4/d43/tutorial_dnn_text_spotting.html)
- PaddleOCR reports 100+ languages at toolkit level and PP-OCRv6’s single unified model is stated to cover 50 languages (Chinese, English, Japanese, and 46 Latin-script languages). This should not be read as every model supporting every script: check the specific model and recognition weights. — [PaddleOCR repository](https://github.com/PaddlePaddle/PaddleOCR)
- RapidOCR model documentation distinguishes language/model variants. Its PP-OCRv6 small/medium recognizers list Chinese, Traditional Chinese, English, Japanese, and numerous Latin-script languages; PP-OCRv5 includes separate recognition models for Cyrillic, Arabic, Devanagari, Tamil, Telugu, Thai, Greek, Korean, and others. Detection model language indications do not guarantee recognition support for the same scripts. — [RapidOCR model list](https://rapidai.github.io/RapidOCRDocs/main/model_list/)
- EasyOCR’s project README lists 80+ languages and scripts including Latin, Chinese, Arabic, Devanagari, and Cyrillic. Tesseract’s language table gives a long catalog of trained data including Latin, Cyrillic, Arabic, Indic, CJK, and other scripts, with model set/version differences. — [EasyOCR repository](https://github.com/JaidedAI/EasyOCR); [Tesseract language data table](https://tesseract-ocr.github.io/tessdoc/Data-Files-in-different-versions.html)
- Project-level licenses: PaddleOCR Apache-2.0; EasyOCR Apache-2.0; MMOCR Apache-2.0; docTR Apache-2.0; Tesseract Apache-2.0; RapidOCR Apache-2.0; OpenCV Apache-2.0. These do not automatically establish the license/usage conditions of every third-party model weight, training dataset, dependency, or packaged language file. RapidOCR explicitly notes upstream Paddle model provenance and links model attribution/license details. — [PaddleOCR](https://github.com/PaddlePaddle/PaddleOCR); [EasyOCR](https://github.com/JaidedAI/EasyOCR); [MMOCR](https://github.com/open-mmlab/mmocr); [docTR](https://github.com/mindee/doctr); [Tesseract](https://github.com/tesseract-ocr/tesseract); [RapidOCR model licenses](https://github.com/RapidAI/RapidOCR/blob/main/MODEL_LICENSES.md); [OpenCV](https://github.com/opencv/opencv)

### Inferences
- For edge/mobile prototypes, RapidOCR or a deliberately selected small Paddle model are the most promising from the documented runtime and size choices; the actual winning configuration depends on target SoC, quantization/backend coverage, input resolution, and language.
- OpenCV is attractive when an application already uses it and needs direct control over the video loop, but its pretrained scene-text examples and language options are less turnkey than multilingual OCR toolkits.
- Licensing review should include weights and bundled dependencies, not just each GitHub repository’s top-level SPDX license.

### Gaps
- No exhaustive legal analysis of model cards, training-data terms, language-data licenses, or dependency licenses was performed. Confirm the exact redistributed artifacts and target commercial use before shipping.
- The presence of Android/iOS folders or browser APIs is evidence of deployment routes, not proof of production support, model parity, or achievable frame rate on a specific device.

## What do published speed claims and maturity signals actually establish?

### Takeaway
Treat vendor speed statements as configuration-specific reference points only. The strongest currently retrieved numeric claim is PaddleOCR’s own PP-OCRv6 report (including a CPU speedup and A100 latency); no source establishes comparable real-time video FPS across frameworks. Measure end-to-end latency and sustained throughput on the intended camera, resolution, language, hardware, and runtime.

### Cited Findings
- PaddleOCR’s README attributes PP-OCRv6 speed claims to its maintainers: 5.2× CPU inference speedup using OpenVINO, 6.1× on Apple M4 for the tiny model, and 0.13 s on A100 GPU. The README also lists tiny/small/medium parameter counts (1.5M/7.7M/34.5M). These are not independently normalized across competing OCR stacks and the cited summary does not fully specify input resolution, batch, warm-up, precision, or whether the 0.13 s includes capture/pre/post-processing. — [PaddleOCR repository](https://github.com/PaddlePaddle/PaddleOCR)
- PaddleOCR’s high-performance inference documentation cautions that first inference can be slower while engine caches are built, and that some models do not accelerate due to graph/operator limitations. This supports separating cold-start from steady-state measurement and checking backend compatibility. — [PaddleOCR high-performance inference](https://paddlepaddle.github.io/PaddleOCR/latest/en/version3.x/inference_deployment/local_inference/high_performance_inference.html)
- OpenCV’s text tutorial provides example model input sizes (e.g. DB detector 736×736 and EAST 320×320) and directs readers to dataset paper results; it does not give an end-to-end live-video FPS claim. Different image sizes and model backbones make raw latency comparisons misleading. — [OpenCV scene-text tutorial](https://docs.opencv.org/4.13.0/d4/d43/tutorial_dnn_text_spotting.html)
- MMOCR’s repository publishes a model zoo and many algorithms but the reviewed README does not provide one general end-to-end real-time speed claim. Benchmarking must select and measure an individual model/config and deployment runtime. — [MMOCR repository](https://github.com/open-mmlab/mmocr)
- docTR documents architecture choices, straight-box fast-path behavior, GPU-ready containers, and serving examples, but the reviewed README does not establish a general video FPS number. Its own note that straight-page assumptions are fastest illustrates the effect of geometric/rectification options on cost. — [docTR repository](https://github.com/mindee/doctr)
- EasyOCR documents CPU/GPU options and the load-once `Reader` pattern, but the reviewed README provides no controlled speed numbers. The CRAFT detection plus recognition pass means scene-level latency depends on image dimensions, number of text crops, GPU/CPU, and preprocessing. — [EasyOCR repository](https://github.com/JaidedAI/EasyOCR)
- RapidOCR advertises fast offline deployment and supports hardware-oriented inference backends; its reviewed main README does not provide a directly comparable quantified latency claim. Backend availability alone does not predict speed because conversion, operator support, precision, and device all matter. — [RapidOCR repository](https://github.com/RapidAI/RapidOCR); [model list](https://rapidai.github.io/RapidOCRDocs/main/model_list/)
- Maturity evidence differs: Tesseract traces its origins to HP work in 1985–1994, has been open source since 2005, and identifies version 5 as the current stable major line. PaddleOCR, OpenCV, and Tesseract have large, long-running ecosystems; EasyOCR is widely used but its repository cites a 2024 latest release; MMOCR has extensive research breadth but its stated v1.0 release is 2023; docTR is actively maintained under a new stated maintainer; RapidOCR has multiple language runtimes and versioned model/docs releases. — [Tesseract repository](https://github.com/tesseract-ocr/tesseract); [PaddleOCR](https://github.com/PaddlePaddle/PaddleOCR); [OpenCV](https://github.com/opencv/opencv); [EasyOCR](https://github.com/JaidedAI/EasyOCR); [MMOCR](https://github.com/open-mmlab/mmocr); [docTR](https://github.com/mindee/doctr); [RapidOCR](https://github.com/RapidAI/RapidOCR)

### Inferences
- A fair camera benchmark should report detector, recognizer, model version/size, image dimensions, device/runtime/precision, warm-up, batch size, per-stage latency, end-to-end p50/p95, sustained FPS and thermals, plus text accuracy/recall on representative motion, blur, glare, angle, and script conditions.
- Video systems can often lower compute by detecting every Nth frame and tracking boxes between detections, then recognizing only new or changed tracks. Such a speedup belongs to the application pipeline and should not be presented as an OCR model’s standalone FPS.
- Public repository stars, commit counts, or “real-time” in a model paper are weak substitutes for maintained releases, reproducible deployment benchmarks, and real target-hardware validation.

### Gaps
- No reproducible, head-to-head video benchmark covering all named projects and identical test conditions was found in the primary material reviewed.
- Exact test setups behind the PaddleOCR README latency figures are not fully described in that summary; they should be treated as official claims, not directly transferable service-level estimates.
- Current GitHub pages are mutable. Maturity observations are point-in-time signals from the reviewed repository documentation and should be rechecked before a deployment decision.
