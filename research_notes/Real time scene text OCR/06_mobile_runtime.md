# Practical real-time scene-text OCR on phones and GPUs

## Camera loop, frame selection, tracking, geometry, and power

### Takeaway

Treat live OCR as an asynchronous, rate-limited vision pipeline rather than running a full OCR stack on every preview frame. A practical design detects periodically or on scene/motion change, tracks existing text regions between detections, and recognizes only stable/high-value crops; benchmark the complete camera-to-overlay loop, not just model inference.

### Cited Findings

- **Measured reference (GPU, not mobile):** PARSeq's repository reports a 14.87 ms median for a batch-1 model call with 32×128 input, using PyTorch's benchmark utility, one thread, and three non-autoregressive refinement iterations. It reports 23.833M parameters and 3.255G FLOPs. The README does not identify the GPU/device for that shown measurement, so this is not a phone latency claim. [PARSeq benchmark and results](https://github.com/baudm/parseq)
- PARSeq's provided `bench.py` generates a single random input and times `model(x)` with PyTorch `blocked_autorange`; it sets deterministic algorithms and disables cuDNN benchmarking. It is a model microbenchmark, not a camera-to-text benchmark. [PARSeq bench.py](https://github.com/baudm/parseq/blob/main/bench.py)
- PaddleOCR describes a multi-stage pipeline and reports model-level vendor benchmarks including PP-OCRv6 tiny 1.5M, small 7.7M, medium 34.5M parameters; its current README claims tiny inference 6.1× faster on Apple M4 and 0.13s on A100 for a listed configuration. These are vendor-reported figures, not independent phone camera-loop measurements; resolution, batch details, and full pipeline parity must be checked before comparison. [PaddleOCR repository/benchmark claims](https://github.com/PaddlePaddle/PaddleOCR)
- CRAFT detects character regions and affinities and derives text boxes with thresholding and minimum-area rectangles. Its official repo has pretrained-model inference and a `--show_time` option, but does not establish modern phone runtime or power measurements. [CRAFT-pytorch](https://github.com/clovaai/CRAFT-pytorch)
- EasyOCR's `Reader` loads detector/recognizer weights once and accepts OpenCV image arrays; this is a useful simple pipeline demo, but its documented usage is Python/PyTorch and provides no mobile live-camera performance measurements. [EasyOCR](https://github.com/JaidedAI/EasyOCR)

### Inferences

- Recommended camera loop (engineering proposal; **not measured benchmark data**): keep camera capture on its own thread; use a bounded latest-frame queue (drop stale frames rather than build latency); run inference asynchronously at a target cadence (initially 3–8 detections/s); then tune from sustained device measurements. Keep preview at camera/display cadence. When frame-to-frame motion is low, reuse the last text layout and track boxes with optical flow or a lightweight tracker; trigger a new detector pass on accumulated motion, track confidence loss, zoom/focus changes, or a periodic refresh. Run recognition only on newly detected/changed crops. The cadence numbers are starting-point estimates, not published device results.
- A robust pipeline separates (1) camera conversion/rotation, (2) detector, (3) polygon/box decoding and NMS, (4) crop rectification, (5) recognizer, (6) temporal association/text stabilization, and (7) UI rendering. Profile each stage and the end-to-end age of the displayed result. Run CPU postprocessing concurrently where practical; avoid redundant full-resolution copies and avoid synchronous GPU/CPU readbacks between stages.
- Carry explicit transform metadata for each frame: camera sensor coordinates → preview-buffer coordinates (including sensor orientation and front-camera mirroring) → resized/letterboxed model tensor → detector coordinates → original image coordinates → view coordinates. Invert transforms in reverse order for overlays. Preserve polygon corners for perspective crop rectification; mapping only axis-aligned rectangles loses rotated-text geometry. Test all four right-angle orientations, mirrored preview, non-square aspect ratios, crop/letterbox padding, and device-specific sensor orientation.
- Track text instances using polygon/box overlap plus appearance/text similarity and confidence; use temporal consensus (e.g. confidence-weighted character/logit aggregation or majority vote over a short stable window), not indiscriminate string averaging. Clear/re-detect after scene cuts, large motion, or failed matching. This is a proposed design, not a sourced measured result.
- Power is a whole-device/system property: camera ISP, preview, memory copies, GPU/NPU activity, display brightness, and thermal throttling all contribute. Public OCR-specific, controlled phone power numbers were not found in the reviewed primary sources; do not infer battery life from model FLOPs or isolated inference latency.

### Gaps

- No apples-to-apples public measurement was identified for a full live scene-text OCR loop on recent iPhone/Android consumer devices with sustained thermal state, camera+preview running, frame-drop behavior, latency percentiles, and energy per recognized frame.
- Public benchmarks inspected do not provide a common device/model/input-size/runtime/power protocol. The M4/A100 PaddleOCR claims and PARSeq microbenchmark should not be directly compared.

## Runtime backends, quantization, and practical demos

### Takeaway

Choose the runtime for the target platform and exported graph, then validate operator coverage and end-to-end accuracy. Core ML is the natural first route on Apple devices; Android should be benchmarked with the platform accelerator that actually executes the graph (NNAPI or vendor-specific QNN/TFLite delegates), with CPU fallback as a controlled baseline. TensorRT is for NVIDIA GPUs/Jetson, not ordinary phones.

### Cited Findings

- ONNX Runtime Mobile targets iOS and Android; its mobile guidance points to model-export helpers, mobile operator references, and ORT format optimization. [ONNX Runtime Mobile](https://onnxruntime.ai/docs/get-started/with-mobile.html)
- ONNX Runtime's CoreML execution provider supports iOS 13+; it can select CPU, GPU, and Neural Engine through `MLComputeUnits` (`CPUOnly`, `CPUAndNeuralEngine`, `CPUAndGPU`, `ALL`). Dynamic shapes can negatively affect performance; static-shape-only execution can be required. Provider operator coverage differs between NeuralNetwork and MLProgram formats. Core ML compilation can take significant time; model caching is available. [ORT CoreML EP](https://onnxruntime.ai/docs/execution-providers/CoreML-ExecutionProvider.html)
- ONNX Runtime's NNAPI provider supports Android 8.1+ (Android 9+ recommended). It can target Android's CPU/GPU/accelerator interface. The documentation warns that NNAPI CPU fallback can be less efficient than optimized ORT kernels and offers a flag to disable that fallback (API level 29+). It supports only documented operator patterns/constraints; partitioning/fallback can therefore materially affect actual execution. [ORT NNAPI EP](https://onnxruntime.ai/docs/execution-providers/NNAPI-ExecutionProvider.html)
- ONNX Runtime's TensorRT EP is an NVIDIA GPU backend and recommends registering CUDA EP beneath TensorRT so unsupported nodes can execute there. It supports FP16 and INT8 options, dynamic-shape profiles, engine/timing caches; the cache is specific to model/settings/runtime and GPU. [ORT TensorRT EP](https://onnxruntime.ai/docs/execution-providers/TensorRT-ExecutionProvider.html)
- **Measured, but not OCR and not phone inference:** ORT documents TensorRT session initialization for a Stable Diffusion UNet as 384 s uncached, 42 s with timing cache, 9 s with engine cache, and 1.9 s with an embedded engine. This demonstrates startup/build cost and cache impact for that particular model, not OCR inference latency. [ORT TensorRT EP cache measurements](https://onnxruntime.ai/docs/execution-providers/TensorRT-ExecutionProvider.html)
- ONNX Runtime supports INT8 QOperator and QDQ representations, static quantization using calibration data and dynamic quantization. Its guidance generally suggests static quantization for CNNs and dynamic for RNN/Transformer models, while warning quantization may reduce accuracy and hardware without efficient INT8 instructions may not speed up. [ORT quantization guide](https://onnxruntime.ai/docs/performance/model-optimizations/quantization.html)
- PaddleOCR documents ONNX conversion and high-performance inference options including ONNX Runtime and TensorRT, and advertises benchmark tooling that can report end-to-end and module-level timing. [PaddleOCR](https://github.com/PaddlePaddle/PaddleOCR)
- PARSeq includes export guidance via its FAQ, a recognition demo, model variants (including PARSeq-Tiny), mixed-case/punctuation charset options and orientation-rotation evaluation commands. Its published 14.87 ms number is explicitly a PyTorch model benchmark and must not be treated as ONNX/mobile latency. [PARSeq](https://github.com/baudm/parseq)
- EasyOCR is a useful end-to-end reference/demo: CRAFT detector plus CRNN recognition, supports Latin and many other scripts, and its API returns boxes, text and confidence. Its own README says compatible languages can be selected together and English is compatible with every language; model loading is done once. It is not a native mobile runtime demo. [EasyOCR](https://github.com/JaidedAI/EasyOCR)
- CRAFT is a practical detector baseline with an official inference demo and downloadable English/multilingual (“Eng + MLT”) general-purpose weights; the repo's listed language coverage is not a Czech-specific accuracy guarantee. [CRAFT-pytorch](https://github.com/clovaai/CRAFT-pytorch)

### Inferences

- **Apple architecture (recommendation):** camera/Metal preprocessing → compact DB-style/CRAFT-like scene-text detector exported to Core ML (or ONNX Runtime CoreML EP) → CPU polygon decode/crop rectification → recognition model on Core ML. Start FP16; compare CPU+ANE, GPU, and ALL on actual supported devices because selecting a compute unit does not prove all operators run on that unit. Prefer fixed input shapes or a small set of shape buckets. Validate Core ML graph conversion and supported ops before optimizing.
- **Android architecture (recommendation):** camera image in YUV where possible → GPU/CPU resize/normalization → detector and recognizer as two independently deployable models → CPU geometry/decode. Compare LiteRT/TFLite with GPU delegate, NNAPI, and Qualcomm QNN where available; ORT NNAPI is an additional portable baseline. Inspect delegates/partition logs: partial accelerator coverage and boundary copies can erase gains. Avoid assuming NNAPI guarantees NPU execution. A single fixed model input shape generally simplifies accelerator compilation and reduces shape variability.
- **NVIDIA GPU/Jetson architecture (recommendation):** export detector and recognizer to ONNX, validate numerical parity, then TensorRT FP16 first; use INT8 only after representative calibration including Czech diacritics, varied scripts, scale/lighting/blur, and rare text crops. Keep CUDA fallback and inspect partitioning. Cache engines for deployment, account separately for engine build/startup and steady-state inference. Desktop GPU throughput figures do not predict phone thermals or latency.
- For a real-time text detector, consider a compact DBNet/DBNet++-style segmentation detector for dense multi-line text; CRAFT remains an interpretable open baseline and can help with character-level localization/irregular text but may incur expensive full-frame maps/postprocess. Use a recognizer selected for export/runtime simplicity: CTC CNN/sequence recognizers are usually simpler to quantize/deploy; PARSeq offers strong recognition and convenient charset controls, but its transformer decoder and 23.8M base size make it a candidate for cropped text or high-tier devices rather than assumed always-on mobile default. These are architecture tradeoffs/inferences, not measured head-to-head results.
- FP16 is a sensible first optimization on Apple/NVIDIA accelerators. INT8 is a benchmark candidate, not an automatic win; calibrate and report OCR accuracy loss by class/condition. For recognition, preserve diacritic distinctions through `á č ď é ě í ň ó ř š ť ú ů ý ž` and capitals; global word-level language correction must not silently erase valid proper names, numbers, brand text, or English strings.

### Gaps

- This review did not find a public, maintained scene-text OCR repository that demonstrates a complete native camera preview + tracking + OCR + cross-platform accelerator pipeline with credible phone energy/thermal measurements. The named projects are model/pipeline examples; a native camera app integration still needs implementation and profiling.
- The current cited sources do not quantify per-provider operator coverage for a specific chosen OCR export or provide an apples-to-apples TFLite/LiteRT vs Core ML vs NNAPI vs ONNX Runtime table.

## Czech+English architecture recommendation and evaluation protocol

### Takeaway

Use one Latin-script recognizer with an explicitly expanded Czech+English character set, and train/fine-tune it on mixed scene text rather than routing language per frame. For a balanced midrange-phone target, the likely practical starting point is a compact detector plus a CTC-based recognizer, selective recognition on tracked crops, and FP16 accelerator inference; benchmark PARSeq-Tiny as an accuracy-oriented alternative. These are **recommendations/estimates** pending a target-device evaluation, not claimed measured results.

### Cited Findings

- PARSeq supports custom character sets; its documented options include mixed-case alphanumeric and mixed-case plus punctuation, and its repository FAQ links to custom-language training/export. Its benchmark scripts include 90°/180°/270° rotation evaluation. [PARSeq](https://github.com/baudm/parseq)
- EasyOCR provides a baseline supporting 80+ languages and Latin script, and its docs describe language selection and per-result boxes, text and confidence. It does not establish that a Czech-English combination has the desired scene-text accuracy. [EasyOCR](https://github.com/JaidedAI/EasyOCR)
- PaddleOCR's current README says its PP-OCRv6 unified model supports 46 Latin-script languages alongside English and provides tiny/small/medium tiers; Czech is within the Latin-script scope claim, but a product-specific Czech-English scene benchmark is not shown there. [PaddleOCR](https://github.com/PaddlePaddle/PaddleOCR)
- CRAFT's official general model lists English plus MLT training coverage. This can serve as detector baseline, but does not directly guarantee Czech text-detection recall or Czech recognition. [CRAFT-pytorch](https://github.com/clovaai/CRAFT-pytorch)
- The public PARSeq recognition results report exact word accuracy 95.95% combined on 7,672 samples across six standard scene-text datasets (lowercase alphanumeric protocol); that benchmark excludes the requested Czech diacritics/mixed-language field protocol and is not a mobile runtime benchmark. [PARSeq results](https://github.com/baudm/parseq)

### Inferences

- **Recommended initial stack (estimated pending measurement):** lightweight DBNet-family detector at a capped long side; polygon/quad crop rectification; mobile CTC recognizer with shared Czech-English Latin alphabet and punctuation; recognition only on new/uncertain crops; track and stabilize between detector passes. Candidate alternate is PARSeq-Tiny for cases where accuracy on perspective, irregular, or ambiguous text outweighs decoder/runtime cost. Evaluate full PaddleOCR PP-OCRv6 tiny/small as an additional ready-made multilingual option; verify export/backend support and local accuracy.
- Build or curate a representative labeled corpus: storefront/signage, transit, street names, product packages, menus, screens, license/serial-like strings if in scope; include real Czech diacritics, uppercase/lowercase, English, code-switching on the same sign, digits, punctuation, stylized fonts, oblique/vertical text, blur, glare, low light, motion, distance, and partial occlusion. Split by capture location/sign/source and recording session, not random adjacent video frames, to reduce leakage. Synthetic training data can expand rare character combinations, but held-out real images/video must decide selection.
- Output metrics: detector precision/recall and polygon F-score at stated IoU/benchmark convention; word exact-match accuracy and normalized edit distance; character error rate (CER) and insertion/deletion/substitution breakdown; results stratified by Czech diacritics, English, mixed line, text scale, angle, lighting, blur, and detector confidence. Include detection misses in end-to-end OCR score rather than reporting recognizer-only crop accuracy alone. Report latency p50/p90/p95 from exposure/frame timestamp to stable overlay, detector cadence, displayed-result age, throughput, dropped frames, RAM/model size, cold start, sustained thermal performance and energy (J/frame or average watts under a specified duty cycle).
- **Reproducible device protocol (proposed):** lock model weights/export hash, runtime/provider/delegate versions, OS/build, camera resolution/FPS, preview path, model input dimensions and thresholds. Test at least one lower/mid-tier and one flagship iOS device and representative Android SoCs (Qualcomm and non-Qualcomm if deployment scope requires). Run a fixed held-out set of short annotated camera sequences under identical lighting/motion plus still-image suite; warm up, then record 5–10 minute continuous runs at room temperature and a controlled warm start. Publish stage timing and end-to-end distributions, not only average FPS; measure battery/rail power with an external meter or calibrated profiler and state method. Repeat runs and disclose device temperature, screen brightness, network state, and whether the GPU/NPU delegate actually claimed the intended graph.
- **Numerical evaluation plan (not a measurement):** first establish FP32/FP16 parity against the reference model; then compare FP16, INT8 PTQ, and (if needed) QAT using identical samples and runtime. Set a preregistered accuracy guardrail (e.g. no more than 1 absolute percentage-point word-accuracy loss overall and no more than 2 points on Czech-diacritic subset) before accepting speed/power gains; these thresholds are proposed product criteria, not published standards. Record model size, initialization, per-stage latency and sustained performance for every backend.
- **Estimate framing:** “real-time” is application-specific; for a responsive overlay, a reasonable initial engineering target could be stable text updates within roughly 200–400 ms while preview remains smooth, with partial results sooner. This is a UX target estimate only, not a measured promise. OCR need not run at camera frame rate if tracking keeps boxes/text current between recognitions.

### Gaps

- No cited public benchmark establishes expected Czech diacritic word accuracy for the recommended mobile models under real camera video, or quantifies the accuracy benefit/cost of adding Czech data to any named released recognizer.
- No device/SoC, minimum phone tier, target app frame rate, acceptable energy budget, or scene-specific corpus was supplied. Final model sizing and cadence must be chosen from the proposed test protocol on the intended product devices.
