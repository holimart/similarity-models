# OCR evaluation dataset licensing, access and fair-comparison design

## Dataset use terms, access and Czech/English suite composition

### Takeaway
Treat software licenses and dataset/model rights separately: PaddleOCR and RapidOCR code are Apache-2.0, and RapidOCR explicitly says its bundled ONNX models derive from PaddleOCR weights, so a PaddleOCR-versus-RapidOCR run may compare deployment implementations of the same trained models rather than independent OCR systems. Use established public sets only where their own terms permit the intended use, then add a newly captured, permissioned Czech/English private set; the private set is essential because no well-established public Czech real-scene OCR test set with word-level ground truth was identified in the primary sources reviewed.

### Cited Findings
- PaddleOCR's repository identifies its project license as Apache 2.0. This license covers the repository work and does not itself establish rights to every included/downloaded dataset or model artifact. — [PaddleOCR README](https://github.com/PaddlePaddle/PaddleOCR/blob/main/README.md); [Apache License 2.0](https://github.com/PaddlePaddle/PaddleOCR/blob/main/LICENSE)
- RapidOCR describes its origin as conversion of PaddleOCR models to ONNX and states in its model licensing notes that bundled/hosted model files derive from official PaddleOCR models; source code and model artifacts are described as Apache-2.0, with upstream attribution/model-specific details. Thus same-weight overlap is expected for matching model families/versions, but verify exact version, architecture, dictionary, and SHA-256 before claiming identity. — [RapidOCR README and license notes](https://github.com/RapidAI/RapidOCR)
- CORD is a public set of 1,000 Indonesian receipts (800 train / 100 dev / 100 test); it contains image and box/text labels and is released under CC BY 4.0. It is useful as an annotation/schema example, but not a Czech/English representative test set. — [CORD repository/data specification](https://github.com/clovaai/cord)
- The widely reused Clova scene-text recognition benchmark's training collection is MJSynth and SynthText; its evaluation collection combines IIIT5K, SVT, IC03, IC13, IC15, SVTP and CUTE. The authors explicitly frame consistent train/evaluation datasets as necessary for fair comparisons, while their distribution packages together images/labels from third-party collections, so downstream reuse must honor each source collection's terms rather than assume the benchmark code's Apache license clears the data. — [Clova benchmark README](https://github.com/clovaai/deep-text-recognition-benchmark); [Baek et al., ICCV/arXiv](https://arxiv.org/abs/1904.01906)
- Benchmark challenge portals may gate downloads/require registration and impose dataset-specific conditions; access being possible through a research challenge or mirror is not equivalent to an unrestricted redistribution license. This review could not reliably retrieve the ICDAR RRC download/terms pages, so check the current official terms for every selected ICDAR release before downloading, publishing images, or using commercially. — [ICDAR Robust Reading Competition portal](https://rrc.cvc.uab.es/)

### Inferences
- Recommended **public, fixed test panel**: (1) ICDAR2015 focused incidental scene text for detector + recognizer end-to-end evaluation, subject to current RRC conditions; (2) a permitted, officially sourced IIIT5K or SVT word-crop recognition test set for recognition-only diagnosis; and (3) a documented public document-image set such as CORD only as an optional receipt/domain panel, not mixed into a real-scene aggregate. Record the exact release/split/terms and do not redistribute data absent permission.
- Do not use benchmark training material or synthetic training sets (MJSynth/SynthText) as test data. The common Clova “evaluation” package includes multiple test corpora and legacy variants; carefully exclude any test subset also used for validation or tuning.
- **Practical private panel**: collect roughly 1,000–2,000 genuinely new images in Czechia, balanced across Czech and English visible text, with consent/permission and documented capture provenance. Stratify across street/store signs, posters/menus/packaging, vehicle/wayfinding, and other everyday scene text; include daylight/night, blur, perspective, small text, occlusion, and mixed-language/diacritic cases. Make about 15% a development set and keep the remainder sealed as a test set; split by physical location, capture session, and source/scene rather than random adjacent frames. This is a proposed design, not a claim about an existing corpus.
- For public reproducibility without rights over images, publish image IDs/hashes, annotation schema, scripts, and aggregate results; distribute the private images/labels only to authorized evaluators. Publish the full private split only if contributor permissions and privacy/third-party rights expressly allow it.

### Gaps
- No primary-source license terms for the individual IIIT5K, SVT, CUTE80, MJSynth, SynthText and each ICDAR release were confirmed in this pass. Treat them as individually unresolved and verify original project/portal terms before use; do not infer rights from papers, mirrors, or the benchmark wrapper license.
- I found no established public Czech real-scene dataset with comprehensive word-level transcription labels in the primary sources examined. This is a bounded search finding, not proof that no such dataset exists; the recommendation is to build a private Czech-scene test panel and describe the public-data gap explicitly.

## Annotation conventions, split integrity and leakage control

### Takeaway
OCR benchmark scores depend materially on label normalization, ignored-region policy, granularity, and split history. Freeze one annotation/evaluation protocol for both systems, preserve raw ground truth, and treat unknown pretraining exposure as a reported risk rather than assume public test images are unseen.

### Cited Findings
- CORD's documented OCR labels include each word's quadrilateral (`quad`) and transcription (`text`), with additional line/group semantics; it demonstrates that word boxes and text need explicit schema conventions. — [CORD data specification](https://github.com/clovaai/cord)
- ICDAR challenge evaluations define task-specific annotations and evaluation protocols (including detection and recognition tasks); results from differently configured challenge tasks are not automatically comparable. — [ICDAR RRC](https://rrc.cvc.uab.es/)
- Baek et al. document inconsistency in training/evaluation dataset choices and resulting performance gaps in scene-text recognition comparisons; they provide a unified evaluation framework specifically to make comparisons consistent. — [Baek et al., “What Is Wrong With Scene Text Recognition Model Comparisons?”](https://arxiv.org/abs/1904.01906)
- The Clova benchmark README notes dataset variants and filtering decisions for benchmark test subsets (including an IC15 evaluation filtering option), illustrating that a named corpus alone does not fully specify the evaluated sample. — [Clova benchmark README](https://github.com/clovaai/deep-text-recognition-benchmark)

### Inferences
- Define task levels separately: **detection** (polygon/box localization), **recognition-only** (human-cropped word image to string), and **end-to-end spotting** (predicted regions and strings). Use the same original image and annotation for both systems; recognition-only crops must be generated from GT consistently, not each model's own boxes.
- Adopt word-level polygons with transcription; retain image-level metadata for language/script, scene/domain, capture conditions and source identity. Mark illegible/ambiguous or out-of-scope text with explicit ignore flags; decide in advance how to treat punctuation, whitespace, case, accents/diacritics, apostrophes, hyphens, currency symbols, and partially occluded words. Publish both raw exact text and a normalized scoring form; primary score should preserve Czech diacritics and case, with any case/diacritic-insensitive score explicitly secondary.
- For detection, report precision/recall and F-score at a specified polygon matching IoU threshold (and the precise ignored/care-region handling). For end-to-end, report the official protocol where available and a consistently implemented word-level precision/recall/F-score. Report recognition normalized edit distance and character error rate (CER); include exact word accuracy and optionally WER, with normalization stated. Aggregate micro and per-image/macro results, and break down Czech/English, scene type and difficulty.
- Split by source unit, not individual image: keep all frames from one video/session, repeated views of one sign, same document/page, same store/location, and duplicate/near-duplicate crops in one partition. Compute perceptual hashes and text/image duplicate checks across train/dev/test; maintain a manifest of public benchmark overlaps and model-pretraining exposure.
- Freeze model and pipeline versions before opening the sealed test. Use development data for threshold/configuration choice only, never report it as test performance. If either vendor has likely seen a public benchmark during training or tuning, report that overlap risk; public pretrained weights' complete training provenance may be unavailable.

### Gaps
- Public sources reviewed do not establish the complete pretraining corpus of current PaddleOCR/RapidOCR weights or whether every common public benchmark image was included in upstream training, validation, or tuning. Exact leakage risk can only be reduced through weight/data provenance checks and the newly collected held-out private set.
- OCR annotation details differ by benchmark release; the official per-release annotation instructions and ignore-region semantics should be inspected before implementing adapters. This research did not confirm a single universal annotation convention.

## Metrics and controlled PaddleOCR-versus-RapidOCR evaluation

### Takeaway
Run two complementary tracks: first compare the same weight files and same task pipeline across runtimes to measure conversion/runtime parity; second compare each product's documented default/best supported configurations to measure practical system quality. Keep speed, accuracy, and implementation conditions separate, because shared weights make quality attribution to the frontend/runtime particularly misleading.

### Cited Findings
- RapidOCR says it converts PaddleOCR models to ONNX and supports inference through multiple engines (including ONNX Runtime, OpenVINO, MNN, TensorRT, Paddle and PyTorch); its project rationale is deployment engineering/performance and portability. — [RapidOCR README](https://github.com/RapidAI/RapidOCR)
- PaddleOCR documents Paddle and ONNX Runtime deployment/inference options and its repository license; the available runtime choices make a matched backend/model comparison practicable, provided preprocessing/postprocessing also match. — [PaddleOCR README](https://github.com/PaddlePaddle/PaddleOCR/blob/main/README.md)
- Baek et al. explicitly motivate consistent data choices and evaluate accuracy, speed and memory under a controlled framework, supporting reporting multiple axes rather than a single accuracy number. — [Baek et al.](https://arxiv.org/abs/1904.01906)

### Inferences
- **Track A — runtime/conversion parity:** select one exact detector+recognizer checkpoint pair shared by both integrations; publish model filenames, hashes, source/version and character dictionary. Hold image decoding, resize/normalization, tiling, batch size, thresholds, crop ordering, orientation handling, recognition decoding, and output filtering constant. Compare Paddle native inference against RapidOCR ONNX Runtime (then optionally the same ONNX graph in Paddle's ONNX backend). Report per-stage and end-to-end latency, throughput, peak RAM/VRAM, model size, and paired per-image accuracy deltas. A score difference here is pipeline/conversion/numerical/runtime behavior, not a different trained model's intrinsic quality.
- **Track B — deployable package comparison:** compare pinned current PaddleOCR and RapidOCR releases using their advertised/default recommended model packs and default configurations; document all model identities and differences. This assesses the out-of-box products, not isolated runtime. Add an optional **matched-quality configuration** comparison using identical model weights/settings across engines.
- Benchmark on the same machine, OS, hardware, driver, thread counts, precision, warm-up, input order and image set. Report CPU and GPU separately; include cold-start/model-load time and steady-state p50/p95 latency, throughput at fixed concurrency, and memory. Avoid comparing one warm GPU run against another CPU/default run. Provide raw per-image predictions and a paired bootstrap confidence interval for accuracy deltas where test permissions allow.
- **Primary quality score**: end-to-end word spotting F-score under frozen matching/ignore rules; alongside detection F-score and recognition-only CER/normalized edit distance. For Czech report exact Unicode with correct diacritics as primary; publish English and Czech strata separately and a macro average so the larger language group cannot swamp the smaller one.
- **Primary operational score**: end-to-end latency at a stated batch/concurrency plus memory on a fixed reference CPU (and optionally GPU), with accuracy shown beside it. Avoid a single blended speed/accuracy score unless the weighting is a predeclared application requirement.
- Publish configuration files, package versions, model hashes, runtime/provider versions, hardware details, preprocessing settings, scoring code, and a table classifying every model pair as identical weights, converted weights, or different weights. Because RapidOCR derives many artifacts from PaddleOCR, list the comparison as **runtime parity** when hashes or documented provenance match; reserve “model quality” conclusions for demonstrably different model checkpoints evaluated under equal conditions.

### Gaps
- RapidOCR's public project statement establishes upstream derivation but the exact matched weight identity varies by model release/configuration; confirm hashes for the concrete chosen detector and recognizer before testing.
- No empirical benchmark results are produced here. Exact speed and quality rankings depend on pinned package/model versions, hardware and operating settings and should be measured using the proposed protocol.
