# Open-weight document parsing systems for invoices and receipts

## Do these systems produce invoice fields, or general document parsing?

### Takeaway
Most tools in this set are document parsers/OCR systems: they recover text, layout, tables, and sometimes bounding boxes, but do not reliably emit a normalized invoice schema (supplier, invoice number/date, tax, total, line-item objects) as a native guaranteed output. Nanonets OCR2 and promptable VLMs can be asked for structured fields, while PaddleOCR also has separate key-information-extraction components; invoice extraction still needs a schema, validation, and document-specific evaluation.

### Cited Findings
- Nanonets-OCR2 is presented as image-to-Markdown OCR with semantic tagging, tables, checkbox/signature/watermark handling, and document VQA; its example prompt returns natural-reading text and HTML tables, not a fixed invoice JSON schema. It includes an alternate hosted Docstrange “Markdown (Financial Docs)” option, distinct from the open 3B model. [Nanonets-OCR2 model card](https://huggingface.co/nanonets/Nanonets-OCR2-3B)
- Nanonets documents a family with OCR2-3B (open HF model), OCR2-1.5B-exp (experimental HF model), and OCR2-Plus (hosted access link). The cited financial-docs output mode is via Docstrange API, so it should not be conflated with locally deployable open weights. [Nanonets-OCR2 model card](https://huggingface.co/nanonets/Nanonets-OCR2-3B)
- olmOCR produces linearized plain text/Markdown in natural reading order and represents sections, tables, lists, and equations; its model and pipeline are optimized for converting PDFs rather than key-value invoice extraction. [olmOCR repository](https://github.com/allenai/olmocr); [olmOCR paper](https://arxiv.org/abs/2502.18443)
- MinerU 4.0 uses a unified document model with Markdown, HTML, LaTeX, DOCX, EPUB, PDF, Structured Content, and Content List exports. Those are structured parsing/rendering outputs, not a purpose-built invoice field schema. [MinerU repository](https://github.com/opendatalab/MinerU)
- Marker exports Markdown, JSON block trees, chunks, and HTML. Its JSON includes block classes, page polygons, and child blocks; Marker calls forms a known limitation and recommends optional LLM-based correction, so key-field extraction is a subsequent task. [Marker repository](https://github.com/datalab-to/marker)
- Docling supplies a structured DoclingDocument and lossless JSON, plus Markdown/HTML and other formats. The repository describes advanced PDF layout/table/formula parsing; it does not advertise invoice-field extraction as a native task. [Docling repository](https://github.com/docling-project/docling); [Docling technical report](https://arxiv.org/abs/2408.09869)
- PaddleOCR-VL outputs Markdown or JSON for document parsing; its PP-StructureV3 path adds coordinate detail including table cells and text coordinates. PaddleOCR separately includes KIE/information-extraction functionality, which is a more direct route to field extraction than treating the VL parser's reading output as an invoice schema. [PaddleOCR repository](https://github.com/PaddlePaddle/PaddleOCR); [PaddleOCR-VL model card](https://huggingface.co/PaddlePaddle/PaddleOCR-VL)
- Granite-Docling-258M converts page images to DocTags/DoclingDocument and is designed as a compact document-conversion component; its documented task interface includes page conversion, table, chart, formula, and region tasks, not a fixed invoice schema. [Granite-Docling model card](https://huggingface.co/ibm-granite/granite-docling-258M)

### Inferences
- For invoices/receipts, separate “page understanding” quality from “field extraction” quality. A parser can produce faithful table/layout content yet fail to map `Total`, `Amount Due`, tax, discounts, or line items to stable semantic fields.
- A practical stack is parser/OCR → constrained schema extraction (prompted VLM or KIE model) → type/arithmetical validation and confidence/review. Keep source text and coordinates for auditable correction.
- Nanonets-OCR2 and PaddleOCR KIE are the closest options in this list to invoice-oriented extraction workflows; none of the reviewed repos/papers provides a directly comparable, current invoice/receipt benchmark proving end-to-end field accuracy.

### Gaps
- No verified standardized invoice/receipt benchmark results were found for these systems on common public datasets such as SROIE/CORD/DocILE with consistent field-level metrics. Published general document parsing numbers should not be treated as invoice F1.
- The HF endpoint `nanonets/Nanonets-Doc-Parse` was inaccessible (401), and the similarly named GitHub repo path returned 404. The directly verifiable open model is Nanonets-OCR2-3B; “Nanonets-Doc-Parse” may refer to a private, renamed, or hosted offering, but its precise weights, license, and current release could not be confirmed.

## Current releases, model size, GPU fit, and licenses

### Takeaway
There is a useful spectrum from CPU-capable classical/hybrid pipelines and sub-billion-parameter VLMs to 7B VLM OCR. PaddleOCR-VL-0.9B and Granite-Docling-258M offer compact learned models; olmOCR-2 7B is explicitly GPU-oriented (project says at least 12 GB VRAM), while Marker/MinerU/Docling are full pipelines whose resource needs depend on selected backend and models.

### Cited Findings
- **Nanonets-OCR2-3B:** HF currently identifies the architecture as Qwen2.5-VL-3B-derived, with BF16 weights (HF model-size widget says 4B parameters). The card demonstrates Transformers and vLLM serving, but does not specify a minimum VRAM figure. Apache/MIT model license was not shown in the accessible model-card text; verify the current model files/card license before commercial adoption rather than inferring from the code repository. [Nanonets-OCR2-3B model card](https://huggingface.co/nanonets/Nanonets-OCR2-3B)
- **olmOCR:** current repository advertises v0.4.0 and `allenai/olmOCR-2-7B-1025-FP8`, a 7B VLM. Local GPU requirements list a recent NVIDIA GPU with at least 12 GB RAM/VRAM and 30 GB free disk; tested devices include RTX 4090, L40S, A100, and H100. Toolkit license is Apache-2.0. [olmOCR repository](https://github.com/allenai/olmocr); [olmOCR 2 report](https://arxiv.org/abs/2510.19817)
- **MinerU 4.0:** current repository presents v4.0 stable, including Flash/Basic/Standard/Advanced parsing tiers and independent ONNX/Torch/VLM runtime choices. Its documentation gives approximate download sizes/minimum system RAM: Basic ONNX ~0.8 GB / 2 GB RAM; Standard/Advanced ONNX plus llama.cpp ~2 GB / 8 GB RAM. NVIDIA acceleration is optional for throughput; CPU/Vulkan is supported. Repository license is presented in `LICENSE.md`; check it and separately check model licenses before deployment, because it is not safe to assume every weight inherits one code license. [MinerU repository](https://github.com/opendatalab/MinerU); [MinerU license](https://github.com/opendatalab/MinerU/blob/master/LICENSE.md)
- **Marker:** code is Apache-2.0, but its model weights use a modified AI Pubs OpenRAIL-M license with commercial restrictions (free research, personal use, and qualifying startups under stated thresholds; broader commercial weight use requires Datalab licensing). Balanced mode is GPU-focused and uses Surya VLM; fast mode emphasizes CPU/text-layer extraction and lightweight layout detector; the repository does not state one fixed universal VRAM minimum. [Marker repository](https://github.com/datalab-to/marker); [Marker model license](https://github.com/datalab-to/marker/blob/master/MODEL_LICENSE)
- **Docling:** library is MIT; individual model licenses remain those of their original packages. Standard pipeline is a multi-model document-processing toolkit, not one monolithic parameterized model. Its optional Granite-Docling VLM has 258M parameters, BF16 model files (~0.3B display on HF), Apache-2.0, and supports Transformers/vLLM/MLX. [Docling repository](https://github.com/docling-project/docling); [Granite-Docling model card](https://huggingface.co/ibm-granite/granite-docling-258M)
- **PaddleOCR-VL:** the original PaddleOCR-VL is a 0.9B compact VLM (HF card rounds model size to 1.0B), Apache-2.0, with the newer PaddleOCR-VL-1.6 advertised in current PaddleOCR repository as a 96.3% OmniDocBench v1.6 model. Do not assume the 1.6 release's exact weight size or VRAM from the older 0.9B card; verify its specific model card. [PaddleOCR repository](https://github.com/PaddlePaddle/PaddleOCR); [PaddleOCR-VL model card](https://huggingface.co/PaddlePaddle/PaddleOCR-VL)
- **Granite-Docling:** 258M model, Apache-2.0, released September 17, 2025. Its small parameter count makes low-memory deployment plausible, but full-page resolution, inference framework, batching, and KV/output allocation determine actual GPU requirements; no authoritative minimum VRAM number was found on the model card. [Granite-Docling model card](https://huggingface.co/ibm-granite/granite-docling-258M)
- Model weights and repository code can carry different terms. This is material for Marker, and also merits explicit per-model review for Docling/PaddleOCR ecosystems. [Marker repository](https://github.com/datalab-to/marker); [Docling repository](https://github.com/docling-project/docling); [PaddleOCR repository](https://github.com/PaddlePaddle/PaddleOCR)

### Inferences
- Rough 16-bit parameter storage alone is approximately 0.5 GB for 258M, 1.8 GB for 0.9B, 6 GB for 3B, and 14 GB for 7B parameters; this excludes vision activation, context/KV cache, runtime, and batching. Actual hardware sizing must be measured at the chosen resolution and concurrency.
- Small weights do not automatically make a full parser small: Docling, Marker, PaddleOCR, and MinerU may load multiple layout/OCR/recognition components alongside a VLM.
- For a single-GPU environment under 16 GB, Granite-Docling or PaddleOCR-VL is a more plausible learned-model trial than olmOCR-2 7B; benchmark actual pipeline memory. CPU-focused Marker fast / MinerU Basic may be appropriate for born-digital documents when scan quality is not central.

### Gaps
- No apples-to-apples published VRAM table covering all named projects and current versions was found. Runtime requirements differ substantially by mode and image size.
- PaddleOCR-VL-1.6's exact deployed model weights, license metadata, and VRAM recommendations should be checked on its distinct HF model card; the older model card alone is insufficient.
- Nanonets-OCR2's license was not reliably established from the retrieved card despite accessible model weights; do not assume Apache-style permissiveness.

## Benchmarks and tradeoffs for invoice/receipt selection

### Takeaway
General document benchmarks show substantial differences in layout and OCR performance, but they measure document reconstruction rather than invoice fields. PaddleOCR-VL, olmOCR, and Marker publish useful general parsing evidence; system-level benchmark claims are versioned and not directly interchangeable, so local invoice-set evaluation should determine selection.

### Cited Findings
- The olmOCR repository's published olmOCR-Bench table (over 7,000 tests / 1,400 documents; version-specific) lists overall scores: PaddleOCR-VL 80.0, olmOCR v0.4.0 82.4±1.1, Marker 1.10.1 76.1±1.1, MinerU 2.5.4 75.2±1.1, and Nanonets-OCR2-3B 69.5±1.1. This is a mixed collection of PDFs testing old scans, math, tables, headers/footers, columns, tiny text, and baseline—not an invoice extraction benchmark. [olmOCR repository benchmark](https://github.com/allenai/olmocr); [olmOCR-Bench](https://github.com/allenai/olmocr/tree/main/olmocr/bench)
- The same olmOCR repo lists its then-current v0.4.0 model at 82.4±1.1 on olmOCR-Bench and states GPU deployment is required for its 7B model. Its paper describes a million-pages cost estimate of $176 for the earlier system and benchmark design; this is a project-reported throughput/cost claim, not a hardware-independent current invoice-processing price. [olmOCR repository](https://github.com/allenai/olmocr); [olmOCR paper](https://arxiv.org/abs/2502.18443)
- Marker repository reports a separate recent run on olmOCR-Bench: Marker balanced 76.0 overall / 83.5 born-digital, MinerU pipeline 72.7 / 83.3 digital-only, Marker fast 66.6 / 71.6, Docling 50.3 / 64.0. It states throughput on one B200 host: Marker balanced 2.9 pages/s, MinerU 0.54 pages/s, Marker fast 7.4 pages/s; these are vendor-reported pipeline results using a stated benchmark harness and hardware, not invoice throughput. [Marker repository benchmarks](https://github.com/datalab-to/marker)
- Marker notes its comparison table uses newer benchmark runs and the same overall macro-average across eight categories, but the numbers do not match the older/versioned table currently present in olmOCR README (e.g. Marker 76.0 vs 76.1; MinerU 72.7 vs 75.2). Treat version/model/pipeline configuration as essential metadata; do not merge the scores into one ranking. [Marker repository](https://github.com/datalab-to/marker); [olmOCR repository](https://github.com/allenai/olmocr)
- PaddleOCR-VL repository/model card advertises a 0.9B architecture and strong performance on OmniDocBench v1.5; current PaddleOCR README advertises PaddleOCR-VL-1.6 at 96.3% on OmniDocBench v1.6. This is the authors' benchmark claim on a different benchmark/version than olmOCR-Bench, not evidence of invoice field accuracy. [PaddleOCR-VL model card](https://huggingface.co/PaddlePaddle/PaddleOCR-VL); [PaddleOCR repository](https://github.com/PaddlePaddle/PaddleOCR)
- Nanonets-OCR2-3B model card reports DocVQA 89.43 and ChartQA 78.56, alongside a nonstandard pairwise Markdown evaluation versus OCR2-Plus; the card does not provide a publicly verifiable invoice/receipt exact-field benchmark. [Nanonets-OCR2-3B model card](https://huggingface.co/nanonets/Nanonets-OCR2-3B)
- Granite-Docling reports full-page OCR edit distance 0.45, layout F1 0.86, and table TEDS with content 0.96 on the card's reported evaluations. These are different test sets and metrics from the document benchmark scores above; no invoice field extraction score is reported there. [Granite-Docling model card](https://huggingface.co/ibm-granite/granite-docling-258M)
- Marker explicitly identifies forms as a limitation and says optional LLM mode may improve form output. Its standard outputs are Markdown/JSON layout tree; for invoice work, this suggests validating form/field mappings and line-item reconstruction separately. [Marker repository](https://github.com/datalab-to/marker)
- Docling is a multi-format, local-capable MIT toolkit with layout, reading order, table, code, formula, and OCR capabilities; Granite-Docling is available as an optional compact VLM pipeline. This favors integration flexibility and license simplicity, but not necessarily best extraction accuracy for every noisy receipt. [Docling repository](https://github.com/docling-project/docling); [Granite-Docling model card](https://huggingface.co/ibm-granite/granite-docling-258M)
- MinerU 4.0's broad tier/runtime/export choices include CPU-capable local inference and structured results. Marker offers fast CPU-friendly text-layer paths and an optional higher-quality VLM mode. These choices are relevant where invoice PDFs are digital versus scanned/photographed, and where throughput/latency competes with parse quality. [MinerU repository](https://github.com/opendatalab/MinerU); [Marker repository](https://github.com/datalab-to/marker)

### Inferences
- Candidate shortlist by use case: (1) PaddleOCR-VL / PP-StructureV3 when compact multilingual parsing, coordinates, and a KIE ecosystem matter; (2) Nanonets-OCR2-3B when prompting to semantically tagged Markdown/HTML and document VQA are attractive, subject to clarifying license; (3) Marker or Docling for local general-purpose parsing pipelines and integration, with model-license scrutiny for Marker; (4) olmOCR where batch PDF linearization fidelity justifies 7B GPU deployment; (5) MinerU where broad supported formats, local tier controls, and structured result contract are useful.
- Receipts often combine low resolution, skew, thermal fading, sparse key-value labels, and unpredictable layouts; invoices add variable line-item tables and tax arithmetic. Test representative originals, not clean benchmark PDFs, and score exact-match/normalized field accuracy, line-item precision/recall, totals reconciliation, abstention, runtime, and VRAM.
- Do not compare the 96.3 OmniDocBench number directly with 82.4 olmOCR-Bench: different datasets, metrics, evaluation protocols, and model versions.

### Gaps
- No single independent, reproducible cross-system test on the same invoice and receipt dataset was located. All comparative choice recommendations are provisional until tested on target documents.
- License and currently downloadable revision should be confirmed at deployment time; public repository main branches/model cards move independently of papers and old benchmark reports.
- For OCR2 named “Nanonets-Doc-Parse,” the relation to Nanonets-OCR2/hosted Docstrange could not be established from primary public sources retrieved here.
